# Automotive Service Churn Early Warning

An R-based early-warning framework for automotive after-sales churn, with
behavioral feature engineering, leakage-resistant validation, prospective
scoring, and model reliability monitoring.

> This repository is a sanitized portfolio edition. It contains synthetic data
> only. Customer records, vehicle identifiers, internal locations, database
> details, fitted production models, and operational risk lists are excluded.

## Why This Project Matters

This project goes beyond churn classification by building a governance
framework that identifies not only high-risk customers, but also when a model
should not be trusted.

The research distinguishes a genuine early-warning problem from apparent churn
signals caused by list-expiration rules or customers who have already completed
their move elsewhere. The final design predicts whether a currently active
vehicle will still be absent three months later.

## Anonymized Study Highlights

- Approximately **419,000 vehicle-month observations** were used for model
  development.
- The frozen training population contained **256 positive events**.
- The first prospective scoring cohort contained **42,895 eligible vehicles**.
- The operational review capacity was fixed at the **top 5%** of ranked scores.
- Paired bootstrap comparisons favored the Champion over the static baseline in
  **95.2%** of replications for PR AUC and Top-5% lift, and **95.0%** for
  Top-5% capture rate.
- A first-generation model produced an **11.1× concentration anomaly** in a
  small segment. Removing the unstable segment effect reduced the maximum
  concentration ratio to **1.06×**.
- The final Champion passed its shadow reliability gate with score
  **PSI 0.00326** and a **1.02× P99 score ratio**.

These are anonymized aggregate research results, not results generated by the
synthetic demo.

## Modeling Design

The frozen `pure_early_warning_v1.1` specification uses:

- **Population:** vehicles still active in the service network, with fewer than
  600 days since the last service and a qualifying within-network relationship.
- **Target:** absent in the third month after the scoring month.
- **Behavior window:** the three months ending at the scoring month.
- **Validation:** purged rolling time splits where every training label matures
  before the validation month.
- **Ranking metrics:** PR AUC, top-5% lift, and top-5% capture rate.
- **Champion:** static vehicle attributes plus six recent service-behavior
  features.
- **Challenger:** static attributes plus recent body-repair count.
- **Baseline:** static attributes only.
- **Governance:** immutable model specification, prospective scoring registry,
  PSI, tail-score drift, and segment-concentration gates.

Location is retained only for monitoring. It is intentionally excluded from all
v1.1 model feature sets.

## Requirements

- R 4.2 or newer
- `testthat` only when running the test suite

The demo pipeline otherwise uses base R so the methodology can be inspected and
run without a large dependency stack.

## Run the Synthetic Demo

From the repository root:

```r
source("scripts/01_run_demo.R", encoding = "UTF-8")
```

The demo:

1. Generates a synthetic monthly vehicle panel.
2. Builds the three-month target using future presence records.
3. Applies the frozen population rules.
4. Runs purged rolling backtests for all three model roles.
5. Fits the Champion on mature labels.
6. Scores a synthetic prospective cohort.
7. Applies the reliability gate.

Generated CSV, RDS, and report outputs are ignored by Git.

## Run Tests

```r
source("scripts/02_run_tests.R", encoding = "UTF-8")
```

Tests protect the target horizon, purge boundary, top-fraction behavior, and
reliability thresholds.

## Interpretation Limits

- Positive events are extremely rare, and the original rolling validation
  covered only three historical validation months.
- Observed behavioral associations are predictive signals, not causal effects.
- A score ranks risk; it does not prove that outreach will recover a customer.
- Intervention effectiveness requires mature prospective labels and a
  treatment-control experiment.
- The first prospective list must remain an observation cohort until its labels
  mature; it must not be described as a proven retention campaign.

See the [model card](docs/model_card_v1_1.md) for intended use, exclusions,
validation requirements, and monitoring rules.

## Privacy and Security

Do not commit raw customer or vehicle data, real identifiers, database
credentials, internal location codes, fitted operational models, scoring
registries, prospective lists, or exported reports. Any public example must be
synthetic.
